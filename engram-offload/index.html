Engram 主机侧卸载：把 27.7 GiB 的查表参数搬出 HBM

Engram 是 V4.1 把「记住静态知识」从层计算里拆出来做成的查表模块。它的表很大， 在 W8A8 导出下每卡约 27.7 GiB 常驻显存。但查哪些表项只取决于输入 token， 可以提前算出来 —— 所以这张表可以放在 host 内存里，每步只把命中的那些行搬回设备。

  • 已实现
  • 默认关闭 · 需显式传参
  • 仅 int8 表
01

一句话结论与适用条件

解决什么问题
Engram 的 int8 表每卡占约 27.7 GiB HBM。这部分显存本可以留给 KV cache 或更大的 batch。
做了什么
表搬到 host 内存（可分页），每步做一次 NPU→CPU 的 id 同步 + 融合 CPU 算子查表去量化 + 命中行 H2D 回传。
换到了什么
换来 HBM 预算。代价是每步多出 host 侧的查表与一次 H2D，以及对 host 内存的占用。
什么时候别开
非 int8 表（fp8 / bf16 会回退到 HBM）、HBM 本来就够用、host 内存紧张、PP 或 DCP 不等于 1。
为什么能提前预取 Engram 的查表 id 是对输入 token 取 n-gram 再哈希得到的，不依赖任何层的计算结果。 所以进层之前就能把 id 算好，表的访问可以和前面的计算重叠。这是整个卸载方案成立的前提。
02

机制：每一步发生什么

DP 共享：共享的是表，不是查表结果

开 dp_shared_memory 后，同一节点内映射同一 TP 分片的 DP 副本共用一份物理 host 表， 而不是每个 rank 各存一份（每 rank 约省 27.7 GB host 内存）。

共享的是只读的 TP 分片表数据（host 上的 int8 codes 与 fp32 scales）， lookup 仍然每个 rank 各执行一次。原因很直接：各 rank 的输入与历史不同，生成的 n-gram hash id 本来就不一样； 要共享查表结果，就得先把 id 汇总到一处再广播回来，多出一轮通信与同步。所以设计上让每个 rank 直接查本地那份共享表。

共享段怎么建起来

vllm-ascend 用 CANN 注册的 UVA 区（SharedUvaBuffer）做这件事；xLLM 在 CPU 上读表， 所以去掉了设备指针 / host 注册那一层，机制就是普通的 multiprocessing.shared_memory 段 加一个 torch.frombuffer 的 CPU 视图。每个「(engram 层, TP 分片)」拥有两个段： codes（[rows, dim] int8）和 scales（[rows, dim // quant_block] float32）。

  1. leader 创建

    组内 rank 0 用随机名建两个段。

  2. 广播描述符

    通过 gloo 组广播名称 / shape / dtype / size / 层 id / TP 分片 / leader 全局 rank / 随机 token。

  3. 非 leader attach 并校验

    校验 size、shape、dtype 和 token，然后各自建 CPU 视图。

  4. 收集错误并栅栏

    engram_all_gather_object 收集每个 rank 的错误，engram_barrier 给所有映射（或所有失败）加栅栏。

  5. leader unlink

    leader 删掉两个名字，自己和所有 attacher 的映射仍然有效。此时状态才是 ATTACHED，leader 单独加载后转 LOADED。

hostname 不是共享成功的证据 hostname 只用于预检分组（比如估算 /dev/shm 容量）。不同物理节点必须可区分； 但同一物理机上处于不同 /dev/shm namespace 的容器（各自挂独立 tmpfs）同样不能共享。 真正的证据是 attach 成功，并且从段尾读回的 token 与 leader 写入的一致（_verify_segment_token）。 /dev/shm 容量检查同样只是预检。这里不要求每个 rank 的 hostname 唯一 —— 同节点多 rank 重名是正常的。
03

配置方式

配置以原始 JSON 字符串经 C++ gflag engram_config 透传到 Python 执行器解析， 命令行参数写作 --engram-config： 

xllm --engram-config '{"cpu_offload":true,"dp_shared_memory":false}'
键默认含义
cpu_offloadfalseint8 Engram 表驻留 host 内存（卸载开关）
dp_shared_memoryfalse节点内 DP 副本共享同一份 host 表。lookup 仍每 rank 各执行一次
默认是全关 不传 --engram-config 时 EngramConfig() 为 {"cpu_offload":false,"dp_shared_memory":false}（等价 {}）， 走 HBM 路径。要开启卸载必须显式传入。部署侧的启动脚本若需要默认开启，由该脚本自行下发参数，xLLM 不感知其形态。

合法与非法组合

// 合法，三选一
{}                                              // 全关：走 HBM 路径
{"cpu_offload": true}                           // 卸载到 host 内存
{"cpu_offload": true, "dp_shared_memory": true} // 卸载 + 节点内 DP 共享 host 表

// 非法，解析期直接 ValueError
{"dp_shared_memory": true}                       // shared 必须配 cpu_offload
{"cpu_offload": false, "dp_shared_memory": true} // 同上
解析是严格的 字段值必须是真正的布尔值，"true" / 0 / 1 一律拒绝； 未知字段、重复 JSON key、非法 JSON 都会报错。设计意图很明确： 一个拼写错误不能静默地把开关关掉。
04

约束

项要求
TP 仅支持 TP ∈ {1, 2, 4, 8}，且 hash 列数必须被 TP 整除。 hash 列数 = (max_ngram_size - 1) × n_heads；V4.1 默认 n_heads=8、max_ngram_size=4 ⇒ 24 列， TP 取 1/2/4/8 均整除。非整除的去量化 / 切分会直接拒绝。
PP / DCP目前要求 PP = 1、DCP = 1
权重格式仅 safetensors / dummy（load_format ∈ {auto, safetensors, dummy}）
量化类型 int8 专属。只有 W8A8（int8）表有 CPU 解码路径； fp8 / bf16 表请求 cpu_offload 会回退到 HBM，请求 dp_shared_memory 则直接报错。
DP 共享依赖 需要节点内 gloo 通信组（HCCL 没有 object 集合通信）与 /dev/shm 空间（启动前按聚合 footprint 预检）
PD 分离 TODO 待 V4.1 Engram 接入 P/D 分离拓扑后，该拓扑将要求 dp_shared_memory=true；当前运行期尚未强制

06

收益与验证强度

项状态说明
HBM 释放量有明确口径W8A8（Eco-Tech int8）导出下每卡约 27.7 GiB
host 内存节省有明确口径开 dp_shared_memory 后每 rank 约省 27.7 GB host 内存
时延代价未量化每步多一次 D2H id 同步 + CPU 查表 + 命中行 H2D，具体占多少未实测
端到端吞吐影响未验证本页不给数字
怎么判断值不值得开 这是一个拿时延换显存的开关，不是纯收益。判断方法：先算开了之后多出来的 HBM 能让 KV cache 容量 / 并发涨多少，再在目标负载上 A/B 测时延代价。 如果多出来的显存并没有转化成更大的 batch 或更长的上下文，那就不该开。
07

风险与待确认

  • 融合算子必须编进二进制：torch.ops.xllm_ops.engram_int8_lookup_cpu 没注册就直接报错，提示重新编译 / 安装。它是卸载路径唯一的去量化实现。
  • 不能移进 ACL 图：host staging pass 不是图安全的。设备 staging 块的地址在捕获时被烘焙进图，之后不能再移动或增长；图可见的那块按最大 bucket 预先分配。
  • 锁页失败要当真：锁页 staging 分配不到时会报出真实原因，而不是悄悄退化成未锁页的 staging。
  • 容器与 /dev/shm：同机不同 namespace 的容器无法共享，预检通过不等于共享成功（见第 2 节）。
  • PD 分离尚未收口：接入后会要求 dp_shared_memory=true，当前未强制。
