03 / 投机解码

DSpark：块并行草稿 + Markov 条件 + 主模型验证

DSpark 是 DeepSeek-V4.1-Flash 的投机解码方案。一个独立的小草稿模型一次猜 5 个 token， 主模型一次最多验 6 个位置，从第一个开始连续对上的全部接受。 这一页讲清三件事：它怎么工作、V4 到 V4.1 改了什么、 我们在昇腾 A3 上按时间顺序做了哪三项优化以及下一步的 prelaunch。

  • 已实现
  • 已实测（A3）
  • γ = 5 · greedy 无损
  • 三项优化测试条件不同
01

一页读懂

先对齐四个词，后面全文复用

单步耗时 = 一次 draft + 一次 verify 的总耗时。

接受长度 τ = 一轮实际产出的 token 数，含 target 自己产出的那 1 个，范围 1–6。

接受率 = 5 个草稿提案里被接受的比例（不含 target 产出的那个）。

TPOT = 平均每个输出 token 的耗时，约等于 单步耗时 ÷ τ。越低越好。

是什么
独立的草稿模型：3 层、纯 SWA 滑窗 128、MoE 为 1 个 shared + 128 个 routed experts（每 token 选 3 个）。 权重在 checkpoint 的 mtp.0/1/2。embedding 和 LM head 与 target 共享且冻结。 它不是主模型内部的 MTP 层。
怎么猜
一次 draft 前向算出 5 个位置的 base logits；再用低秩 Markov 头做 5 步顺序修正（每步看前一个 token 的偏置），得到 5 个提案。
怎么验
主模型一次验 [anchor, d0…d4] 共 6 个位置。greedy 下从第一个开始连续对上的全部接受； 之后 target 总会再产出 1 个 token —— 有拒绝时是纠正 token，全中时是第 6 位的预测（bonus）。 这个 token 就是下一轮的 anchor。
为什么快
论文公式 L = (T_draft + T_verify) / τ：每 token 耗时 = 单步耗时 ÷ 接受长度。 三条杠杆 —— draft 更快、τ 更大、verify 更省。我们这三项优化动的是第一条和第三条。

我们做了什么

单并发 TPOT 15.3 ms draft 入图后。入图前（成块 + MC2）为 20.91 ms；c=1、greedy、γ=5
draft 设备时间 5.3 ms / 步 图内 body + LM head + Markov。来自另一次 profile，与上面的 15.3 ms 不是同一次测量
整步大头仍是 verify 55.3 ms profile 单步拆解 79.7 ms 中的 verify 部分，是主模型工作量，与 draft 优化无关
引用这些数字前必读

三项优化的测试条件不同：成块是并发 4，MC2 和入图是并发 1。 百分比不能相加也不能相乘。

15.3 ms（压测得到）与 79.7 / 55.3 / 5.3 ms（profile 单分片得到） 不是同一次测量，不能用 79.7 ÷ 15.3 去反推接受长度。

02

原理：三个部件，各管一件事

传统 MTP 是串行的：第 k 个草稿 token 依赖第 k−1 个，只能一步一步来。 DSpark 先把 5 个位置一次并行算出来，再把丢掉的块内依赖补回去。

  • ① 块并行草稿 —— 一次前向出 γ 个位置

    输入是 [anchor, mask×(γ−1)]，位置 p…p+γ−1。 mask 是训练好的占位 token（论文叫 mask token，代码里叫 noise token，同一个东西）。 块内 5 个位置互相可见（双向、非因果）并共享同一段尾窗上下文，所以可以一次算完。 块宽 γ = num_speculative_tokens = dspark_block_size = 5。

  • ② Markov 条件头 —— 把块内依赖补回来

    并行算的时候每个位置看不到"前一个草稿 token 是什么"，依赖丢了。 Markov 头是个很小的修正项：markov_w1 把前一个 token 压成 256 维， markov_w2 投回词表得到一个 bias，当前位的 logits = base + bias。 第 0 位看 anchor，之后每一位看前一位选出的 token。 γ 步串行，每步只做一次 embedding + 一次线性 + argmax。

  • ③ 置信度头 —— 给每个位置一个存活概率

    把当前位的 hidden 和前一个 token 的 Markov 嵌入拼起来，过一层线性 + sigmoid， 得到 0–1 的条件接受概率；前缀各位相乘就是前缀存活概率。 它不参与提案生成，只给调度器提供"这一位值不值得验"的分数。 V4.1 默认构建，但本部署不开 adaptive，所以它不影响已生成的提案。

三句话分工：Markov 补依赖、target 保正确、confidence 供调度。

一个最常见的误解 draft 模型不是主模型内部的 MTP 层。它是独立加载的模型，有自己的 3 层权重和自己的 SWA KV 缓存。 它的上下文由 target 喂：主干 40 层里取第 37/38/39 层（dspark_target_layer_ids）的残差流， 经 main_proj 投影后作为 draft 每层注意力的 KV。 所以"改 draft"和"改主模型"是两条可以分别评估的线。
V4.1 的取点位置与 V4 相差一层

dspark_target_layer_ids 在 V4.1 指这几层的输入残差流 （即进入第 37/38/39 层注意力之前的残差流，等于第 36/37/38 层的输出；4 条 mHC 流取平均）。 官方 reference 的注释原文：reads the attention input of its target layers, not their output。

V4 的同名字段指层输出。照搬 V4 实现会整体错位一层。 这是一个实测过代价的坑：同树同二进制、只差取点位置，接受率差 18 个百分点量级。

03

一次 decode step：从 anchor 到下一个 anchor

这条链路就是 DSpark 的全部内容，也是后面所有优化的作用对象。 先记住它，第 8 节再回来看哪几段被搬进了图。

  • ① 取 anchor

    取上一轮 target 产出的那个 token 和它的位置 p。它还没被 target 前向过，所以 draft 的上下文只到 p−1。

  • ② context KV 注入

    把 target 第 37/38/39 层的残差流经 main_proj 投影，生成 draft 每层要用的 KV，写进 draft 自己的 SWA 缓存。

  • ③ draft 块前向

    输入 [anchor, mask×4]，位置 p…p+4；5 个位置互相可见，共享同一段尾窗上下文。

  • ④ Markov × γ

    串行 5 步。本部署 greedy，每步 argmax(base_k + 低秩偏置(prev))；prev 是 anchor 或上一位选出的 token。

  • ⑤ target verify

    主模型一次验 [anchor, d0…d4] 共 6 个位置（本部署固定 6 位），每个位置都出 logits。

  • ⑥ 接受判定

    从第一个开始连续对上的全部接受；再加 target 产出的 1 个 token —— 有拒绝时是纠正 token，全中时是 bonus。

  • ⑦ 缓存与下一步

    用 verify 输入端有效前缀的 target 残差流更新 draft KV；target 产出的那个 token 成为下一轮 anchor。

位置与可见性：这张图解释了"块"到底长什么样

猜错不影响正确性，但不是零成本

接受的是连续前缀；第一个错的位置用 target 的预测纠正，后面的草稿丢弃。 所以 greedy 下输出和只跑 target 逐 token 完全一致（无损）。最坏情况是这一轮只产出 1 个 token。

代价在 verify：被拒绝的位置也算了一遍。 低并发时几乎免费，高并发时会挤占 batch 容量 —— 这正是论文引入置信度调度的原因。

04

draft 模型结构：3 层、3 个头、一个投影

draft 很小：一个输入投影 + 3 个解码层 + 3 个输出头。 算力很小，但如果每个算子都从 host 逐个发，发射时间会比计算还长 —— 这是理解第 8 节那项优化的前提。

组件作用关键点
main_proj / main_norm target 残差流 → draft hidden 把 3 个捕获层的残差流拼成 3H（3×5120）再压回 H；列并行 + all-gather；官方导出 BF16，也支持 W8A8
3 个解码层 draft 主体前向 纯 SWA 滑窗 128；每层写自己的 KV；MoE 为 1 shared + 128 routed / top-3；残差流同为 mHC 4 路。没有 Engram、没有哈希路由
LM head hidden → 全词表 logits 与 target 共享权重并冻结；但整图路径要求 draft 自己从 checkpoint 加载一份，不能运行时借用 target 的模块
Markov 头 γ 步条件采样 低秩（rank 256）；每张卡放一份、不切分，每步无跨卡通信
置信度头 每位置存活概率 默认构建；生产不开 adaptive，所以不影响提案

最后一层把 mHC 的 4 路残差副本折叠回 1 路，再 norm，然后过 LM head 出全词表 logits。

两个"复制"决定 Markov 头与置信度头在所有并行分片上都放一份，不做切分。 这样每步采样不需要跨卡通信 —— 这也是 Markov 链能整图捕获的直接原因。
一个必须说清楚的约束：全词表 V4.1 的 draft 是全词表的（draft_vocab_size == vocab_size，没有 d2t 映射表）。 d2t 是「draft id → target id」的映射；没有它，提案 token 可以直接喂给 target 验证。 如果某个 checkpoint 用了热词表 + remap，整图路径会在启动阶段拒绝，不会静默降级。
05

V4 → V4.1：改的是训练阶段和专家几何

先给结论：DSpark 的算法骨架没变。 变的是训练阶段的组织方式，和 draft 自己的 MoE 几何。

维度V4-Flash（V4 代 DSpark）V4.1-Flash
训练阶段 backbone 预训练带 MTP（V4 报告：Flash 的 MTP 深度 1）；线上先用 MTP-1，V4-preview 发布两周后被 DSpark 替换 backbone 预训练去掉 MTP；DSpark 在预训练后的独立阶段训练，backbone 冻结；post-training 与 backbone 联合但 DSpark 梯度不回传
训练目标 CE 0.1 + TV 0.9 + confidence 1.0；位置权重 w_k = exp(−(k−1)/γ)，越靠前权重越高 同一套目标；V4.1 报告未给权重
主模型 routed / top-k 256 / top-6（V4-Flash config） 384 / top-6（Tech Report §2.2）
draft routed / top-k 无独立字段，推断沿用主模型 256 / top-6 1 shared + 128 routed / top-3（官方 config）
置信度头 和 draft 一起端到端训练，再用 STS（逐位置温度缩放）校准 逐位置的条件接受概率，供调度器选验证长度
推理侧不变的部分 anchor-first、γ 宽非因果块、一次 draft 前向出 5 个位置、γ 步 Markov、target 一次最多验 γ+1 位
哪些是确证的，哪些是推断

官方 config 可查：V4.1 draft 128 routed / top-3；V4.1 主模型 384 routed / top-6； dspark_target_layer_ids=[37,38,39]；V4-Flash config 没有独立的 draft 专家字段。

推断（未经官方确认）：V4 的 draft 沿用主模型 256 / top-6 的几何。 如果这条推断成立，那么 V4.1 的 draft 比 V4 代更小， draft 的容量、延迟和显存占用都不同 —— 但算法流程不变。

训练配方（数据、loss 权重、token 数、学习率）不在本页范围。

术语对齐（展开）

routed experts = 每层可路由的专家数；top-k = 每个 token 激活几个专家； CE = 交叉熵（学下一个 token）；TV = 让 draft 分布接近 target 分布，直接提高接受率； confidence = 用公式算出的期望接受率监督置信度头； STS = Sequential Temperature Scaling，在留出集上逐位置做温度缩放，把累积存活概率校准到实测接受率； mHC = 把残差流扩成 4 路副本、用 Sinkhorn 归一化矩阵混合的超连接（见 架构页）； W = 一次 draft 的块宽（本模型 5）；MTP = 多 token 预测（上一代串行方案）； 梯度不回传 = DSpark 训练不改 backbone 参数。

06

优化 ① draft 成块执行：把 γ 个位置一次算完

第一刀不在图，而在几何。

原先 draft 的 5 个位置被拆成 5 条单行序列分别下发（q_len=1，一行一个 token）。 每条都按"一个序列"处理，有两个问题：

  • 窗口和掩码与训练时的块语义（块内双向可见）对不齐；
  • 历史 KV gather 和 attention 要各做 5 遍。

改成一次提交一个完整的 5 行块：

维度成块前成块后
query 几何5 × q_len=11 × q_len=5
历史 KV gather5 次1 次
attention 外层循环5 次1 次
可见窗口逐行近似尾 128 + 整个块，非因果

关键：5 个位置共享同一段上下文、块内非因果，才能一次算完。 这不是"把 5 次算得更快"，而是"把 5 次变成 1 次"。

实测

测试条件 昇腾 A3 · 并发 4（与后两项的 c=1 不同）· γ=5 · MC2 关 · draft eager（未入图）· 每组 16 请求。
指标改前改后Δ
每步步长115.9 ms89.8 ms−22.5%
服务端 TPOT29.0 ms22.9 ms−21%
加权接受率0.6410.645持平
这组数字最重要的信息不是 −22.5% 而是接受率没有明显变化。收益来自少做重复工作，不是牺牲接受率换的。 但注意：每组只有 16 个请求，0.641 → 0.645 的差异在这个样本量内不可区分。 只能说"没观察到下降"，不能说"提升"。
07

优化 ② target MoE 开 MC2：把通信融进计算

成块之后（draft 仍是 eager 逐算子执行），一步的大头是 target verify。 verify 的 MoE 层要做 all-to-all 通信：把 token 发给各专家（dispatch），再收回来（combine）。 MC2 把这两步通信和专家计算融在一起，减少单独等通信的时间。 它只作用于 target，draft 不参与。

draft 为什么不能用 MC2 draft 在各 DP 分片上的行数天然不等：有请求的分片跑整块（5 行/序列）， 空闲分片只跑 1 行占位（dummy row）。 MC2 的 decode 路径假设各分片行数相等，否则跨分片写入会乱。所以 draft 不开 MC2，target 侧照常开。

实测

测试条件 昇腾 A3 · γ=5 · 并发 1 · draft 未入图（eager）。
指标MC2 关MC2 开Δ
TPOT21.64 ms20.91 ms−3.4%
出词吞吐45.44 tok/s46.87 tok/s+3.1%
每步时间88.2 ms83.8 ms−4.4 ms

两组结果的分布有重叠，属小幅收益，建议补重复测量。 单步降 5.0% 而 TPOT 只降 3.4%，是因为两组的接受长度略有差异 （88.2/21.64 ≈ 4.08，83.8/20.91 ≈ 4.01）。

边界 MC2 只换 MoE 层的通信，不覆盖 attention 层的并行 all-reduce； 它是配置级优化，不是 DSpark 专属。 部署时要按最大图 batch 预留通信缓冲（本案例 512 MB 量级）： 缓冲不够，图捕获阶段会直接报错。
08

优化 ③ draft 入图：把 body + LM head + γ 步 Markov 整体捕获

draft 的瓶颈不在"算"，在"发"。把 3 层前向 + LM head + 5 步 Markov 采样一起录成一张固定形状的 ACL 图，之后每步只回放一次。

结果

测试条件 昇腾 A3 · γ=5 · greedy · 并发 1。
单并发 TPOT 20.91 → 15.3 ms −26.8%
每步 draft 设备时间 5.3 ms 图内 body + LM head + Markov
整步时间（profile） 79.7 ms 其中 verify 55.3 ms 是大头

TPOT 来自压测，79.7 / 55.3 / 5.3 ms 来自另一次 profile（单分片），两者不是同一次测量。

三个关键设计

  • ① 导出仍按"每行一个 token"

    执行器仍然按一行一个 token 导出，注意力后端再把这 5 行重新拼成一个 5 行块。 这样执行器的原有假设不用改。

  • ② 按"完整块"补齐，而不是按 token

    图是固定形状的，所以按序列桶补齐：token_rows = 序列桶 × γ。 例如 DP4、max_seqs=32 时每 rank 最多 8 个序列，桶是 1/2/4/8 → 5/10/20/40 行； DP2 同配置每 rank 16 个序列，会多一个 16 → 80 行。 桶集合随 DP 和 max_seqs 变化，不是固定四种。 draft 按 sequence 补、target 按 token 行补，两套桶不能混用。

  • ③ 不支持就拒绝，不静默降级

    启动时检查：ACL 图、greedy、CP=1、全词表、draft 已加载自己的 head 权重、非 adaptive。 带 penalties（采样惩罚）或 JSON 约束的请求在准入阶段直接拒绝并返回错误。 图执行异常也直接报错不降级 —— KV 和运行状态可能已经改了一半，不能假定可以安全重试。

09

下一步 prelaunch：把下一轮 draft 先排进去，再等 accepted

三项优化之后，一步里还剩一段 host 空等，记作 H： verify 结束后，host 要等 accepted（target 接受的 token）从设备回到 host（D2H）， 再修输入、建 draft 的 attention metadata、提交 draft 图 —— 这段时间设备闲着。

prelaunch 把下一轮 draft 提前排进设备队列，draft 的输入改在设备上生成，让 host 的准备和 verify 重叠。 论文 §5.2 的生产系统用的是同类思路：Zero-Overhead Scheduling 要求下一步的 batch 在当前步完成前就确定，调度器因此改为异步。

收益模型：V、D、H 分别是什么

verify（V）55.3 ms设备时间，不可省
draft（D）5.3 ms设备时间，已经在图里
host 空泡（H）≤ 19 ms上界，未实测
19 ms 是上界，不是 H 的实测值 19.1 = 79.7 − 55.3 − 5.3 是 profile 的差值。 这个差里还含 context KV 写、图间空泡、engine host 开销，不是 H 本身。 先用 host 时间戳把 H 量出来，再决定 prelaunch 值不值得做。

draft 能开始执行要同时满足两个条件：verify 完成（V）和 host 把 draft 排进队列（H）， 所以开始时间是 max(V, H)，优化后一步总时间 T' = max(V, H) + D。

情形T'被藏掉增益
H < V（预期）V + DHH
H > VH + DVV

H 的上界 19 ms 远小于 V（55 ms），所以预期是第一种：H 被 verify 完全盖住，收益就是 H。

prelaunch 与 draft 入图：作用在不同的 host 开销上

prelaunch 不是入图的替代品。入图省掉的是 draft 逐算子下发的 host 开销； prelaunch 要藏的是入图之后仍然存在的 H。入图没有消掉这两段，所以两者可以叠加。

组合谁省掉什么预期建议
只入图（当前） 消掉 draft 的逐算子下发；H 仍在 已落地，TPOT 20.91 → 15.3 ms（c=1） 保留：确定性最高
只 prelaunch（关图） 把 eager 的 H 藏到 verify 后面 净收益 ≈ 藏起的 eager H − 放弃的图收益（约 5.6 ms/token），可能为负 不作为首选
入图 + prelaunch 入图消掉下发开销，prelaunch 藏住 H 增量 = 入图后的 H（≤19 ms/步，未实测） 目标形态，需图输入也设备化

正确顺序：入图（已做）→ draft 设备 metadata → 量出 H → prelaunch 验证 → 图 + prelaunch。 如果 H 只有 2–3 ms，prelaunch 的收益有限，优先级应让给接受率优化。

适用边界与常见问题

项当前边界
采样 / 并行 greedy；CP=1；全词表 draft；整图要求 draft 加载自己的 head 权重；不支持 penalties / JSON_OBJECT / adaptive（整图路径下这类请求被拒绝）
性能结论 入图和 MC2 只有单并发（c=1）数据，成块是 c=4。多并发、H 实测和 prelaunch 的正式复测是下一步
平台 昇腾 A3。A5 需要重新确认 page size、算子与图捕获约束
收益口径 三项优化来自不同测试条件，不能相乘 / 相加；15.3 ms（压测）与 79.7 ms（profile）也不是同一次测量。引用时必须带条件

这些是当前实现的支持边界，不是模型能力边界。

三个常见问题

  • 为什么块并行不掉质量？

    输出质量由 target 验证保证：greedy 下接受的都是 target 自己会选的 token， 输出和只跑 target 逐 token 一致（无损）。 块并行和 Markov 头只影响接受长度，也就是速度。

  • 入图会不会改变数值？

    图是把同一串算子录下来之后一次播放，理论上不改变计算； 但图融合和执行顺序仍可能带来数值差异，所以上生产前会做标准数据集的精度对齐。

  • prelaunch 能带来多少？

    上限是入图之后剩下的 H（profile 上界 19 ms/步，未实测）。 先用 host 时间戳量出 H，再决定是否投入；H 小于 2–3 ms 就不值得做。

如果只记一件事 draft 侧的瓶颈不在"算"，而在"发"。 把 draft 的 3 层前向、LM head 和 5 步 Markov 链整体录进一张图，单并发 TPOT 从 20.91 降到 15.3 ms。 整步的大头仍是 verify（约 55 ms）。 下一步 prelaunch 把 verify 之后的 host 空等藏进 verify，收益上限是 H，要先实测。
