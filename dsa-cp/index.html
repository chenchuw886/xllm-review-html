04 / 注意力并行 · DeepSeek-V4.1

DSA CP：KV 整份复制，只切 query 的 token 行

常规 TP 把注意力按头切：每个 rank 拿 n_heads / TP 个头，但要处理全部 token 行。 DSA CP 反过来：每个 rank 拿全部 64 个头，但只处理 1/TP 的 token 行； 算完用一次 all-to-all 把「本地 token × 全部头」换成「全部 token × 本地头」，交还给原来的 O 投影。

  • 已实现
  • 默认关闭
  • 仅 Python V4.1 路径 · 仅 NPU
01

一句话结论与适用条件

解决什么问题
V4.1 的稀疏注意力里，有一部分工作是按 query 行计费的（逐行的稀疏取数与 metadata）。按头切 TP 并不能把它分摊，每个 rank 都要对全部 token 行做一遍。
做了什么
在 TP 组内按 query token 行把一次前向的打包 token 切成等长的连续片。KV 不切、整份复制。各 rank 算完自己那片的全部头，再 all-to-all 换回标准布局。
什么时候开
Python 路径的 DeepSeek-V4.1、NPU、tp_size > 1、cp_size = 1、n_heads 能被 tp_size 整除。
什么时候别开
cp_size > 1（会直接报错）、tp_size = 1（不生效）。它不省显存：KV 是整份复制的，而且每个 rank 要存完整的 wq_b 权重。
实现对标 模块 docstring 写明这是「TP-token DSA CP with replicated KV, matching vLLM Ascend's legacy DSACP」， 即对齐 vLLM-Ascend 的旧版 DSACP 语义，不是一个新设计。
02

机制：切 query 行，再换回来

因果长度要跟着改

切完行以后，每个 query 行能看到多少 KV 必须重算，否则因果性就错了。DsaCpContext.local_context_lengths() 做这件事：

  • prefill：对每个请求，用 query_suffix（该请求落在本 rank 之后、被切走的尾部行数） 把全局 KV 长度减回来，并把本 rank 没有行的请求置 0。
  • decode（每行一个 query）：图里的行是固定的，但 KV 长度每次回放都在变。 所以用 torch.arange 在设备上构造 owner mask，本 rank 不拥有的行长度置 0 —— 不把 host 常量拷进图。
图模式下的两个约束

decode 的 ACL 图里，每个常驻请求行只有一个 query。代码用 is_acl_graph 判断后直接取 [1] * seq_lens_q.numel()，避免 .tolist() 在 capture 期触发同步。

计划对象缓存在当前 ForwardContext 的 layer_shared_cache 里，而不是跨 context 复用。 原因是图入口会在 warmup 和 capture 之间复用 execution context，缓存在 ForwardContext 才能保证长度算术被重新捕获、 并在每次回放时读到常驻的设备端长度。

三处关键代码事实

# 1. 开 CP 时每个 rank 持有全部头，而不是 n_heads // tp
num_heads = cfg.n_heads if self.enable_dsa_cp else cfg.n_heads // tp

# 2. 因此 wq_b 的权重不再按头切分（加载时 shard dim 为 None）
("attn.wq_b", "self_attn.q_b_proj", None if attn.enable_dsa_cp else 0)

# 3. 换轴：本地 token × 全部头  →  全部 token × 本地头
send = (padded.view(tokens_per_rank, world_size, local_heads, width)
        .permute(1, 0, 2, 3).contiguous().view(-1, local_heads, width))
received = distributed.all_to_all(send, world_size, "tp")
return received[: num_tokens]
04

启用方式与约束

--enable_dsa_cp=true
条件不满足时
cp_size = 1直接抛错：enable_dsa_cp cannot be combined with cp_size > 1
n_heads % tp_size == 0直接抛错：enable_dsa_cp requires n_heads divisible by tp_size
tp_size > 1静默不生效（enable_dsa_cp and tp > 1）
NPU 后端配置解析阶段 CHECK 失败：enable_dsa_cp is only supported on NPU.
gflag 帮助文本与代码不一致（待确认） enable_dsa_cp 的帮助文本写的是「…for prefill and chunked prefill. Requires cp_size=1; decode keeps the original TP path」。但 dsa_cp.py 里有专门处理 decode ACL 图的分支 （is_acl_graph 时取 [1] * rows），attention forward 里的启用判断也没有区分 prefill / decode。 以代码为准：decode 同样会走 CP 路径。这段帮助文本看起来是旧的，尚未在仓里修正。
与 FlashComm1 互斥

V4.1 的 _validate_flashcomm1 把 enable_dsa_cp 列为否决条件之一。 两个开关都传 true 时，FlashComm1 被静默关掉（只留一条 warning），DSA CP 照常生效。

原因是两者都在切同一个 token 轴：DSA CP 切 attention 的 query 行， FlashComm1 切 row-parallel 之后的激活行。叠加会把序列切两次。 所以它们的收益不能相加估算，要在目标配置上各自实测再取其一。 见 FlashComm1 的准入门禁。

05

收益与验证强度

本页不给 before/after 数字 我们手上的 enable_dsa_cp 实测绑定在另一代模型与平台的组合上，口径不能平移到 Python 路径的 V4.1。 按本站的规则，没有在当前配置下实测过的数字就不写。要用它请自己在目标配置上做 A/B。

收益来自哪里 / 不来自哪里

关闭 DSA CP开启 DSA CP
每 rank 的 query 行数全部 token约 1/TP
每 rank 的头数n_heads / TP全部 n_heads
KV 显存按 TP 分摊整份复制，不省
wq_b 权重按头切分每 rank 一整份
注意力段的通信O 投影后 all_reduce多一次 all_to_all，O 投影后仍 all_reduce

所以它不是一个省显存的特性，也不改变注意力的总 FLOPs。它能赚的是那些 按 query 行计费、无法靠切头分摊的开销：逐行的稀疏取数、metadata 组织、小算子下发。 这部分在 V4.1 的稀疏注意力里占比不小，但具体占多少必须在目标配置上用 profiling 确认。

做 A/B 时注意 开 CP 后每个 rank 只剩很少几行 query（尤其 decode），很多「按 token 行补齐」的优化会因此失去收益空间 —— 这类优化单独测可能有效，和 DSA CP 同开就归零。两个特性要一起测，别把各自的收益相加。
06

风险与待确认

  • 帮助文本与实际 decode 行为不一致（见第 4 节），依赖该文本做部署判断会出错。
  • 每 rank 多存一份完整 wq_b，HBM 预算要相应留出。
  • 与其他「按 token 行切分」的优化存在收益重叠，不能叠加估算。
  • 与 cp_size > 1 的 PCP 路径互斥，两者不能同时用。
