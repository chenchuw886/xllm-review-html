02 / Prefill 序列并行

FlashComm1：让每个 TP rank 只处理自己那份 token

Tensor Parallel 把权重切开了，但 row-parallel 线性层后的 AllReduce 又让每个 rank 拿回一份完整序列。 于是 TP 个 rank 对同一批 token 把归一化、残差混合这些逐 token 的工作各做一遍。 FlashComm1 把这一步换成 ReduceScatter：求和的同时就按 token 行切好， 之后到下一个"必须看完整序列"的边界之前，每个 rank 只留约 S/TP 行。

  • 已实现（两条线）
  • 默认关闭
  • 仅 prefill
  • 与 DSA CP 互斥（V4.1）
01

一句话结论与适用条件

解决什么问题
长 prompt 的 prefill 里，TP 组内每个 rank 都持有完整的 [S, H] 激活。 逐 token 的那部分工作（RMSNorm、mHC 残差混合、逐行写回）和中间激活的显存，都被重复了 TP 份。
做了什么
把 row-parallel 层后的 all_reduce 换成 reduce_scatter， 在必须看完整序列的两个边界（attention、MoE 路由）处再 gather 还原。
什么时候开
长输入 prefill（默认阈值 8192 token）、TTFT 是主要指标、TP > 1。 输入越长、TP 越大，被省掉的重复工作越多。
什么时候别开
短输入（低于阈值不触发）、decode 或长输出占主导、只看 TPOT 的场景。 它完全不介入 decode 循环，不要指望 TPOT 受益。

仓里有两条独立的实现线

同一个开关名 --enable_flashcomm1，背后是两套各自独立的代码。 读这一页之前先确认你在哪条线上，否则门禁条件和收益口径都会对不上。

实现线覆盖模型核心类型切分载体
C++ 线 DeepSeek-V4（models/llm/deepseek_v4.h）、Qwen3-Next（qwen3_next_hybrid_base.h） FlashComm1Context + thread-local FlashComm1ContextScope TP group 内的 reduce_scatter / gather，可选 MMRS 融合算子
Python 线 DeepSeek-V4.1（python/models/deepseek_v41.py）、Qwen3.5、Kimi-K3 SpMetadata + EpSpTokenLayout（显式传参，无 thread-local） TP reduce_scatter / all_gather，MoE 侧换成 EP 组的 gather / reduce-scatter
修正一条过期结论

在 #686 （feat: swa bounded replay & fc1 support.，2026-11-05）之前， 建立 FlashComm1 作用域的只有 deepseek_v4.h 和 qwen3_next_hybrid_base.h 两处， Python 路径的 DeepSeek-V4.1 给 --enable_flashcomm1 确实不生效。

#686 之后 V4.1 有了自己的 Python 实现（build_flashcomm1_layout → sp_shard → 层内边界）。 如果你手上有 2026-11-05 之前的 V4.1 profile，上面那条"开关无效"的判断对那次测量仍然成立， 但不能再用于当前代码。

02

机制：一次 collective 同时完成求和与切分

先说清楚被省掉的到底是什么，再看怎么省。

AllReduce 省不掉重复，只是把重复藏起来了

row-parallel 线性层把权重按输入维切开，每个 rank 算出的是一份部分和（partial sum）， 形状仍是完整的 [S, H]。要拿到正确结果必须跨 rank 相加。 AllReduce 相加之后把同一份完整结果发给每个 rank，于是：

  • 通信量：每个 rank 收发完整的 S × H；
  • 后续计算：下一个 row-parallel 层之前的那些逐 token、不跨 token的算子（RMSNorm、残差加、mHC 的折叠与展开），每个 rank 都对全部 S 行各做一遍；
  • 显存：这段区间的中间激活在每个 rank 上各存一份完整副本。

ReduceScatter 做的是同一次求和，但只把第 r 份切片发给 rank r。 通信量降到约 1/TP，而且输出天然就是切好的，后面那段逐 token 的工作每个 rank 只做自己的 S/TP 行。

为什么这能变成 TTFT 收益 通信量降到约 1/TP，安全区段的逐 token 计算也降到约 1/TP → prompt forward 更早结束 → LM head 和采样更早拿到首 token → 用户更早看到第一个字。
三句不要说的话

不要说"算力严格降到 1/TP"。attention 和 MoE 专家计算这两段必须看完整序列，它们的工作量一行都没少。省的是边界之间那段逐 token 的工作，加上通信量。

不要说"它是上下文并行（CP）"。CP 切的是序列、跨 rank 分摊 attention 的 KV；FlashComm1 切的是 row-parallel 之后的激活行，attention 仍在完整序列上算。两者在 C++ 线上可以叠加（见第 5 节）。

不要把 decoder 末尾的 token-layout gather 和 LM head 的词表并行 logits 归并混为一谈，那是两件事。

03

层内边界：哪几段在切片上跑

FlashComm1 的全部难点就在这张图上：哪些算子可以在切片上算，哪些必须先还原完整序列。 判据只有一条 —— 这个算子要不要跨 token 看别的行。

一个容易写错的细节：bias 必须在 reduce_scatter 之后加

sp_row_parallel_projection 的顺序是 matmul → sp_reduce_scatter → + bias。 row-parallel 层的 bias 只能加一次；如果在归并前加，TP 个 rank 各加一份，求和之后就变成 TP 倍。 

def sp_row_parallel_projection(linear, value, layout):
    partial = ...                      # 各 rank 的部分和，完整 S 行
    output = sp_reduce_scatter(partial, layout)   # 归并 + 切片
    if linear.bias is not None:
        output = output + linear.bias  # 切片上加一次
    return output

05

准入门禁：三层，任一层不过就静默走原路径

两条线都遵守同一个纪律：不满足条件就回退到原执行路径，不报错、不崩。 代价是"开了没生效"很难自己发现，所以这一节值得读完。

第一层 · 启动期静态门禁（仅 Python 线）

_validate_flashcomm1 在建模型时跑一次。任一条不满足，就把开关置回 False 并打 warning，之后整个进程都不再尝试。

条件为什么
quant_mode == 昇腾 W8A8切片路径上的 MoE 只实现了 V4.1 的 W8A8 bias 路由 + 分组专家计算
tp_size > 1TP=1 时没有可切的对象
cp_size == 1 且 enable_dsa_cp == False这两个也在切 token 轴，叠加会把序列切两次
moe_tp_size == 1共享专家要是各 rank 复制的，才能只在本地有效行上跑
ep_size == tp_size × dp_size
ep_rank == dp_rank × tp_size + tp_rank		EP 的 rank 排布必须是 DP-major，否则 EpSpTokenLayout 算出的分发行数对不上实际 rank
first_k_dense_replace == 0 且 moe_layer_freq <= 1要求全部层都是 MoE 层；dense 层没有这条 EP 归并路径
flashcomm1_min_prefill_tokens >= 2阈值小于 2 没有意义
实际部署里最容易踩的一条

enable_dsa_cp 和 enable_flashcomm1 在 V4.1 上是互斥的。 两个都传 true，结果是 FlashComm1 被静默关掉（只留一条 warning），DSA CP 照常生效。

如果你的部署脚本里两个开关都在，那 FlashComm1 从来没跑过。 启动日志里搜 V4.1 FlashComm1 disabled 就能确认。 两者的取舍见 DSA CP 那一页：它们切的是同一个 token 轴，收益不可叠加估算。

C++ 线怎么和 CP 组合

CP 和 FC1 都切 token 轴，但切的组不同（cp_group vs tp_group）， 在 rank 排布 dp_rank × (cp_size × tp_size) + cp_rank × tp_size + tp_rank 里这两个维度是正交的。 只要 CP 在外、FC1 在内就能组合：CP 先把 batch 切到各 cp_rank，FC1 再把每个 cp_rank 的行切到各 tp_rank。 代码为此把原来混用的一个 token 数拆成三个：

字段含义用途
global_num_tokensCP 切分之前的 DP-local batch，CP 组内每个 rank 相同阈值判定用它，保证开关决策在整个 CP 组内一致
local_num_tokens本 rank 在 CP 切分之后的行数所有 padding 几何用它，并成为 ctx.original_num_tokens
min_local_num_tokensCP 组内最小的 local_num_tokens组合门槛：必须 >= tp_world_size × 16

最后一条的原因：V4 的 CP 切分是按序列连续切的，段长不均，短 batch 会让高 cp_rank 只剩很少甚至 0 行。 每个 rank 都能从全局 q_seq_lens 自己推出这个最小值（不需要通信）， 所以用它做门槛可以让 FC1 在整个 CP 组内要么全开要么全关，不会出现一部分 rank 切了、另一部分没切。

CP 开着时 MMRS 会被强制关掉 ctx.enable_mmrs_fusion = options.enable_mmrs_fusion && !cp_active。 融合算子本来就对 shape 敏感（这也是它默认关闭的原因），CP 之后的本地行数更小更不规整。 非融合的 reduce_scatter 路径数值等价，所以在 CP-local shape 上测过之前先用它。

第三层 · Python 线的每步 DP 投票

Python 线的决策必须在所有 DP 副本上一致 —— MoE 的 EP 集合通信是整组参与的， 一个副本切了另一个没切，分发行数就对不上。build_flashcomm1_layout 的做法：

  • 先挑出"活跃"副本

    raw_dp_execution_token_counts 大于 0 的副本才算活跃。空闲副本的 decode 标志是任意的，不参与投票。

  • 活跃副本全是 prefill 才继续

    任何一个真实的 decode 副本直接否决整组。混合 prefill / decode 的那一步，所有副本都走原路径。

  • 阈值取活跃副本的最大行数

    max(counts[active]) >= flashcomm1_min_prefill_tokens。用复制过的 metadata 判定，所以每个 rank 算出同一个结论。

  • 空闲副本照样参与集合通信

    它们不参与投票，但一旦整组通过，它们仍要进 EP 的 gather / reduce-scatter，否则集合通信挂住。ep_apply_local 对 0 有效行的副本直接返回全零。

06

启用方式与参数

核心收益一个开关就够：

--enable_flashcomm1=true

MMRS 融合是 C++ 线上的可选增量，只在 enable_flashcomm1=true 时才被读取：

--enable_flashcomm1=true \
--enable_mmrs_fusion=true
gflag默认值作用范围说明
enable_flashcomm1false两条线总开关
flashcomm1_min_prefill_tokens8192两条线prefill token 数达到该值才允许启用
enable_mmrs_fusionfalse仅 C++ 线Matmul + ReduceScatter 融合算子。默认关闭，因为融合内核在部分 shape 上会失败
mmrs_comm_modeaiv仅 C++ 线torch_npu MMRS 的通信模式：aiv / ai_cpu / none

Python 线没有 MMRS 路径，走的是普通 distributed.reduce_scatter。 给 V4.1 传 --enable_mmrs_fusion 不会报错，也不会有任何效果。

阈值要按模型和 TP 调，8192 不是推荐值 收益拐点同时取决于模型规模、TP 大小和 padding 占比。 默认 8192 是一个偏保守的通用起点。 各模型的部署脚本应该给经过实测的值，而不是沿用默认。

量化 MMRS 的一个实现细节

C++ 线的量化 MMRS 是异步下发的，融合算子返回后它的输入张量还不能释放。 retain_quantized_mmrs_launch_tensors 把 activation、activation scale、weight scale 存起来， 累计超过 512 MB 时做一次 torch::npu::synchronize() 清空； 最外层 FlashComm1ContextScope 析构时也会清一次。 这是显存与同步次数之间的取舍：阈值调小会更省显存但同步更频繁。

收益与验证强度

测试条件（只对 C++ 线成立） DeepSeek-V4-Flash W8A8C16 · Atlas A3 · EP16 / DP4 / TP4 · 输入 8K · 并发 32。 换任何一项条件，下面的数字都不成立。
配置TTFT相对 baseline
Baseline10211.2 ms—
FlashComm1（序列分片）—约 −11.8%

拆开看：序列分片贡献约 −11.8%，MMRS 再额外贡献约 −1.8%。 核心收益不依赖 MMRS —— 这也是 MMRS 默认关闭不影响主收益的原因。

验证强度

结论强度说明
C++ 线在上述单一条件下的 TTFT 收益已实测一组条件、未做多轮重复，不给误差区间
Python V4.1 线的收益未验证#686 刚合入（2026-11-05）。本页不给 V4.1 的数字：C++ 线的 −13.4% 是另一代模型 + 另一套切分载体，口径不能平移
其他模型 / shape / 并发的拐点未验证阈值的最优值随模型变化，需各自实测
MMRS 在未覆盖 shape 上的稳定性未验证已知会在部分 shape 上失败，这是它默认关闭的原因
TPOT 收益不应宣称FlashComm1 不介入 decode 循环

想自己测的话

最小可信的一组对照：

  • 只翻 enable_flashcomm1 一个开关，其余参数与二进制完全相同；
  • 两边都确认日志：开的那边有 FLASHCOMM1_ACTIVE（Python 线）且没有 V4.1 FlashComm1 disabled；
  • 输入长度要明显高于阈值，否则测的是"没触发"；
  • 看 TTFT 分布而不是单次值，冷启动至少 2 轮；
  • 精度侧：切分本身是数值等价的变换，但通信顺序和 reduce 顺序会变，浮点累加次序随之变化，所以上生产前要做一次精度对齐。
08

风险与待确认

  • 静默回退很难发现。 两条线都是"不满足就走原路径"，不报错。 开了之后一定要用日志确认真的生效，否则会把"没触发"误读成"没收益"。
  • V4.1 上与 DSA CP 互斥。 见第 5 节。两个开关都传的部署，FlashComm1 没在跑。
  • Python 线的收益还没有绑定条件的实测。 代码在仓里（#686），机制可读，但我们没有在当前配置上做过 A/B。这一页因此不给 V4.1 的数字。
  • MMRS 融合内核在部分 shape 上会失败。 开启前要在目标 shape 上先验证；CP 开着时它会被强制关掉。
  • 短输入可能为负。 补齐到 TP × 16 的开销、两次 gather 的开销，在短序列上可能吃掉收益。阈值只是保底，过了阈值不代表一定赚。
  • 待确认：Python 线在 chunked prefill 下，各 chunk 的行数差异对 EP 变长分发的 padding 重排有多大开销；这段代码（ep_reduce_scatter 的 variable 分支）会做一次逐 rank 的拷贝重排，成本未测。
