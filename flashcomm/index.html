01 / Prefill 通信优化

FlashComm：让每个 TP rank 只处理自己那份 token

问题不是「算不动」，是「重复做」。Tensor Parallel 把权重切开了，但 row-parallel 线性层后的 AllReduce 又让每个 rank 拿回一份完整序列。FlashComm 把这一步换成 ReduceScatter： 通信在求和的同时就完成了按 token 的切分，之后的安全区段每个 rank 只留约 S/TP 行。

  • 已实现
  • 默认关闭
  • 仅 prefill · 仅 NPU
01

一句话结论与适用条件

解决什么问题
长 prompt 的 prefill 里，TP 组内每个 rank 都持有并处理完整的 [S, H] 序列，通信量和可分片区段的计算量都是重复的。
做了什么
把 row-parallel 层后的 all_reduce 改成 reduce_scatter，在需要完整序列的边界处再 gather 还原。可选再把 matmul 和 reduce_scatter 融成一个算子。
什么时候开
NPU 后端、长输入 prefill（默认阈值 8192 token）、cp_size=1、prefill 在端到端时延里占比高（如 8K/128、32K/1K）。
什么时候别开
短输入（低于阈值不会触发）、长输出 / decode 占比高的场景、cp > 1。它不改 decode 路径，不要指望 TPOT 直接受益。
先说清楚适用的模型范围 FlashComm 的上下文由模型 forward 建立。当前仓里建立这个 scope 的只有两处： xllm/models/llm/deepseek_v4.h（DeepSeek-V4，C++ 路径）和 xllm/models/llm/qwen3_next_hybrid_base.h（Qwen3-Next）。 Python 路径的 DeepSeek-V4.1 没有建立这个 scope，给它传 --enable_flashcomm1 不会生效。
02

机制：一次 collective 同时完成求和与切分

输入 → 处理 → 输出。

两层能力，收益来源不同

能力做法覆盖范围地位
序列维度分片 all_reduce → reduce_scatter，边界处 gather 还原 所有 dtype（BF16 与各类量化） 核心，收益主要来源
MMRS 融合算子 matmul + reduce_scatter → npu_mm_reduce_scatter_base BF16 与 w8a8_dynamic 两条路径 可选增量，默认关闭

两个实现细节

  • Padding：全局 token 数向上补齐到 TP × 16 的倍数（kFc1LocalTokenAlignment = 16）， 保证各 rank 的 collective 等长；最终 gather 后截回真实 token 数。
  • Fallback：MMRS 的 dtype、shape、bias 或运行条件不满足时，退回普通 matmul + reduce_scatter。 数值一致，只是少了 kernel 融合，FlashComm 的核心语义仍然成立。
为什么这能变成 TTFT 收益 AllReduce 复制完整序列 → 多个 TP rank 重复处理相同 token → 长 prefill 的通信和可分片计算成本偏高。 ReduceScatter 在归并时直接完成序列分片 → 安全区段每 rank 只处理约 S/TP 行 → prompt forward 更早结束 → LM head 和采样更早拿到首 token → 用户更早看到第一个字。
表述边界

这是「减少重复的 token 处理和中间激活复制」，不是「所有算力严格下降到 1/TP」。

decoder 末尾的 token-layout gather，和 LM head 的词表并行 logits 归并，是两件不同的事，不要混为一谈。

04

启用方式与约束

核心收益（序列分片 + reduce_scatter）一个开关就够：

--enable_flashcomm1=true

MMRS 是在此基础上的可选增量，只在 enable_flashcomm1=true 时才被读取：

--enable_flashcomm1=true \
--enable_mmrs_fusion=true
参数默认值说明
enable_flashcomm1false总开关
enable_mmrs_fusionfalseMatmul + ReduceScatter 融合算子。默认关闭，因为融合内核在部分 shape 上仍可能失败
flashcomm1_min_prefill_tokens8192prefill token 数达到该阈值才允许启用
mmrs_comm_modeaivtorch_npu MMRS 通信模式，可选 aiv / ai_cpu / none

开关打开后，还要同时满足运行条件才会真正生效：

  • NPU 后端
  • 处于 prefill 阶段
  • cp_size = 1
  • token 数达到阈值
  • TP group 可用

任一条不满足就走原有执行路径，不报错。

阈值要按模型调 flashcomm1_min_prefill_tokens 的最优值与模型参数量相关，不同模型的收益拐点不同。 默认的 8192 是一个偏保守的通用起点，不是推荐值。建议在各模型的部署文档里给经过验证的配置。
05

收益与验证强度

测试条件 DeepSeek-V4-Flash W8A8C16 · Atlas A3 · EP16 / DP4 / TP4 · 输入 8K · 并发 32。 换任何一项条件，下面的数字都不成立。
配置TTFT相对 baseline
Baseline10211.2 ms—
FlashComm（序列分片）—约 −11.8%
FlashComm + MMRS8840.9 ms约 −13.4%

也就是说：序列分片贡献约 −11.8%，MMRS 再额外贡献约 −1.8%。 核心能力不依赖 MMRS，这也是 MMRS 默认关闭不影响主收益的原因。

验证强度

  • 已实测：上面这一组条件下的 TTFT。
  • 未验证：其他模型、其他 shape、其他并发下的收益拐点；MMRS 在未覆盖 shape 上的稳定性。
  • 不应宣称：TPOT 收益。FlashComm 不介入 decode 循环。
06

风险与待确认

  • MMRS 融合内核在部分 shape 上会失败，这是它默认关闭的原因；开启前需要在目标 shape 上先验证。
  • Python 路径的 DeepSeek-V4.1 不受这个开关影响（见第 1 节）。如果在 V4.1 上看到了差异，原因不在 FlashComm。
  • 短输入场景下，切分、gather 和调度开销可能抵消收益。阈值机制只是保底，不代表过了阈值就一定赚。
