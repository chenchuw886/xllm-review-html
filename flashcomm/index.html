01 / WHY

问题不在“算不动”，而在重复做

Tensor Parallel 把权重切开，但 Baseline 的 Row-Parallel 输出经 AllReduce 后，每个 rank 又拿回一份完整序列。长 Prompt 越长，这份重复越贵。

BEFORE

AllReduce：每张卡都有完整答案

各 rank 的 Matmul 局部结果先求和，再把完整 [S, H] 广播给所有 rank。

TP ranks×full S rows=重复 token work
AFTER

ReduceScatter：求和后直接分片

同一次 collective 完成“求和 + 按 token 切分”，每个 rank 只留下 [S/TP, H]。

TP ranks×S/TP rows=刚好覆盖 S
一句话：FlashComm 不减少模型层数，也不改变输出；它减少的是 TP ranks 之间不必要的完整序列复制与可分片区段的重复处理。

04 / MECHANISM

两层优化，先核心、后融合

CORE主要收益

Sequence Shard + ReduceScatter

Matmul→ReduceScatter→[S/TP, H]
  • 由 --enable_flashcomm1=true 开启
  • 所有已接入 dtype 都可走普通 RS 路径
  • 在完整序列边界按需 AllGather
OPTIONAL额外增量

MMRS Fused Operator

Matmul+ReduceScatter→1 op
  • 当前覆盖 BF16 / w8a8_dynamic
  • 减少 kernel launch 与通信调度
  • shape 不支持或执行失败时回退普通 RS
MMRS 未命中≠FlashComm 失效核心分片路径仍然成立

05 / EVIDENCE

最终收益：更早拿到首 token

参考 workload 下，序列分片贡献主要收益；MMRS 是在核心路径之上的额外增量。

06 / ACTIVATE

四个门槛，同时满足才生效

条件不满足时 context 保持 disabled，自动走原路径。

01开关enable_flashcomm1= true
02阶段Prefill非 Decode
03并行CP = 1复用 TP group
04长度tokens ≥ 8192*默认阈值
推荐从核心路径开始 
--enable_flashcomm1=true
验证 shape 稳定后，再评估 MMRS 
--enable_flashcomm1=true \
--enable_mmrs_fusion=true

* 8192 是保守默认值。真正的 break-even 与模型、并行度、dtype、输入长度和并发有关，应以实测为准。

07 / TAKEAWAY

最后，只记住三句话

01

不改模型语义

同一份模型、同一个 TP group；只改变中间通信与张量布局。

02

主收益来自分片

ReduceScatter 让安全区段每个 rank 只处理自己的 token rows。

03

用户感知是首字更快

长 Prefill 更早结束，首 token 更早采样并转成文字；Decode 不直接加速。
